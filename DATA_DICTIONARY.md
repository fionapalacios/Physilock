# Physi-Lock — Final Entities & Data Dictionary

Companion document to the Functional Decomposition Diagram (User: 21 functions, Admin: 6
functions). Where the FDD lists *what each actor does*, this document lists *what data each
actor's functions read or write* — the final entity set as implemented in code, not a design
guess. Every entity, column, type, and constraint below was read directly from the current
schema (Firestore `Account`/`firestore.rules`, and all 19 Room `@Entity` classes under
`data/entity/`) on 2026-09-14, the same day the `LoginEvent → CachedAccount` foreign key was
added (see `MODULE_PROGRESS.md`).

## Two data stores, one account model

Physi-Lock is a hybrid system (see `PROJECT_DOCUMENTATION.md`): **Firestore** (cloud) is the
single shared source of truth for accounts/authentication, reachable by both actors from any
device. **Room/SQLite** (on-device) is a *per-installed-device* local store — it has no
multi-user table structure, because only whichever account is currently signed in on that
device reads/writes it. Most Room tables therefore have no "owning account" column at all;
this was confirmed by the full per-entity FK audit done the same session (see
`MODULE_PROGRESS.md`, "Add foreign-key constraints" item).

## Final entity list, by actor

**Shared / Account & Access** (both actors touch these — User registers/logs in and owns the
account row; Admin authenticates, manages, and reads it for governance/analytics):
`Account` (Firestore), `Username` (Firestore), `CachedAccount` (Room), `LoginEvent` (Room)

**User-owned** (16 entities — local behavior, feature, and configuration data generated by
the signed-in User's own device use):
`UserConfiguration`, `AppUsageLog`, `UsageSession`, `ExcessiveUsagePredictionLog`,
`MotionInterventionLog`, `AppLockRule`, `FocusSession`, `FocusBlockedApp`, `DeepWorkSession`,
`DeepWorkSchedule`, `PomodoroSession`, `PomodoroBlockedApp`, `AllowlistedApp`, `CategoryGoal`,
`ReflectionEntry`, `NotificationLog`

**Admin-owned** (2 entities — global data Admin curates/configures for every device, per the
agreed Admin scope in project memory):
`AppCategory`, `DefaultSettings`

21 entities total (4 shared + 16 User + 2 Admin — `LoginEvent` and `Account`/`Username` also
feed Admin's "View Usage Analytics" / "Manage User Accounts" functions, which is why they sit
in the Shared group rather than being double-counted).

## Legend

- **PK** — Primary Key (uniquely identifies the row)
- **FK** — Foreign Key (references another entity's PK)
- **Relationship** — cardinality/description of the link, including *informal* (non-enforced)
  join keys, which are called out explicitly since Room does not declare most of them

## Shared / Account & Access Entities

### 1. `Account` (Firestore collection `users/{uid}`)

The single account record for both actors; `role` distinguishes User from Admin. Document ID
= Firebase Auth UID. Firebase Auth itself owns email/password verification — this document
holds everything Auth doesn't.

| Column Name | Constraints | Data Type | Description | Relationship | FK | PK |
|---|---|---|---|---|---|---|
| id | Document ID; not stored as a field (`@Exclude`) | String (Firebase Auth UID) | Repopulated via `.copy(id = document.id)` after every read — never trusted from stored data | Referenced by `CachedAccount.id`, `LoginEvent.accountId` (informally, across stores) | No | Yes |
| username | Required; must be unique app-wide (enforced via the `Username` lookup, not a Firestore constraint) | String | Handle used for login-by-username and display | Joins to `Username.username` (its document ID) | No | No |
| fullName | Required | String | Display name | — | No | No |
| email | Required; must match `request.auth.token.email` on writes to `Username` | String | Login identifier; owned by Firebase Auth, mirrored here for profile display | Joins to `Username.email` | No | No |
| occupation | Optional | String? | Free-text profile field (e.g. student/employee), shown on Edit Profile | — | No | No |
| role | Required; self-`create` locked to `"USER"`, self-`update` cannot change it — only Admin can (`firestore.rules`) | String enum (`Role.USER`, `Role.ADMIN`) | Governs Admin-only screens/actions app-wide | — | No | No |
| createdAt | Required; defaults to write time | Long (epoch ms) | Account creation timestamp | — | No | No |
| isActive | Required; self-`update` cannot change it — only Admin can (`firestore.rules`) | Boolean | Admin's activate/deactivate control (Manage User Accounts) | — | No | No |

### 4. `LoginEvent` (Room table `login_events`)

One row per account per calendar day it was seen signed in. Backs Admin Analytics' "Daily

## Notes on non-enforced ("informal") relationships

Most `packageName`-keyed tables above (`AppCategory`, `AppLockRule`, `AllowlistedApp`,
`FocusBlockedApp`, `PomodoroBlockedApp`) and the app-tagged log tables (`AppUsageLog`,
`UsageSession`, `MotionInterventionLog`) all describe the *same real-world app* when their
`packageName` values match, and `CategoryGoal.categoryType` likewise lines up with
`AppCategory.category`'s enum values. None of these are declared as Room `@ForeignKey`s today
— they're joined at query time by matching string values, not enforced by the database. This
was confirmed deliberately, not missed: a full FK audit (2026-09-14, see `MODULE_PROGRESS.md`)
found `LoginEvent.accountId → CachedAccount.id` is the only column in the entire local schema
that stores an actual owning-row reference Room can enforce; every other apparent link above
is a shared *value*, not a stored *reference to another row's key*, so adding a formal FK to
`AppCategory.packageName` (for example) would constrain "this app must already be categorized
before it can be locked" — a real rule, but a product decision, not something this pass
assumed.
